API reference

Clients and transports

REDCap.AbstractREDCapClient — Type
AbstractREDCapClient

Supertype of REDCapProject and REDCapSuperUser. A client holds the API URL, a token and a transport. Every API function takes a client as its first argument.

source
REDCap.REDCapProject — Type
REDCapProject(; url=ENV["REDCAP_API_URL"], token=ENV["REDCAP_API_TOKEN"],
                transport=HTTPTransport(), allow_insecure=false)

A client for one REDCap project, holding a 32-character project API token.

url and token fall back to the environment variables independently, and only when the client is constructed, so REDCapProject(token=ENV["STUDY_A"]) works. The URL must have the form https://…/api/; plain http:// is accepted only with allow_insecure=true.

show prints only the last four characters of the token.

source
REDCap.REDCapSuperUser — Type
REDCapSuperUser(; url=ENV["REDCAP_API_URL"], token=ENV["REDCAP_API_SUPER_TOKEN"],
                  transport=HTTPTransport(), allow_insecure=false)

A client holding a 64-character super API token, which can create projects (see create_project). Otherwise behaves like REDCapProject.

source
REDCap.AbstractTransport — Type
AbstractTransport

Sends a REDCapRequest and returns a REDCapResponse. Implementations define REDCap.send_request(transport, request).

source
REDCap.HTTPTransport — Type
HTTPTransport(; kwargs...)

The real transport, which POSTs requests with HTTP.jl. TLS certificates are always verified and HTTP.jl's automatic retries are disabled, since writes are not safe to repeat. Extra keyword arguments (e.g. timeouts) are passed on to HTTP.post.

source
REDCap.MockTransport — Type
MockTransport(handler)
MockTransport(responses::REDCapResponse...)

A transport for tests. It records every request it receives in requests and answers with handler(request) (any callable returning a REDCapResponse), or with the given responses in order. It never touches the network.

source
REDCap.RecordingTransport — Type
RecordingTransport(inner, dir)

Wraps another transport (usually HTTPTransport) and saves every request/response pair to a JSON fixture file in dir, for replay in tests.

Tokens are removed: the token field is dropped, the request's token is replaced wherever it appears, and the project token returned by create_project is replaced with zeros. Only the Content-Type and Content-Disposition headers are kept. Fixtures can still contain personal data (record values, usernames, logging): review them before committing.

source

Data, results and errors

REDCap.REDCapTable — Type
REDCapTable

The column table returned by every table-valued export. It implements the Tables.jl interface, so it can be passed to any Tables.jl sink, e.g. DataFrame(t).

Values are kept exactly as REDCap sends them: usually Strings (empty strings stay empty strings), with nested JSON objects as Dict{String,Any} cells. A cell is missing only when REDCap omitted that key from a row entirely.

Access a column with t[:name] or Tables.getcolumn(t, :name).

source
REDCap.REDCapFile — Type
REDCapFile(path)

Marks path as a file whose contents should be sent unchanged as an import's data, together with an explicit format. A plain String is never treated as a file name.

source
REDCap.REDCapDownload — Type
REDCapDownload

A file exported from REDCap: filename (from the response headers; may be empty), mime type, and the file's bytes in data. Save it with write(path, d.data).

source
REDCap.REDCapError — Type
REDCapError <: Exception

Thrown when REDCap answers a request with a non-2xx HTTP status, or with a response that can't be converted to the method's declared return type.

Fields

  • status::Int: the HTTP status code
  • message::String: REDCap's error message, taken from its {"error": "..."} JSON body when present, otherwise the raw body text
  • method::Symbol: the name of the REDCap.jl function that made the request

The API token never appears in a REDCapError.

source
REDCap.REDCapBatchError — Type
REDCapBatchError <: Exception

Thrown when one batch of a batched call (batchsize=...) fails, whether REDCap answered with an error or the request itself failed (for example, a timeout or connection error). Batched calls are not atomic: the batches before the failed one stay applied. An InterruptException is not wrapped.

Fields

  • completed_batches::Int: the number of batches that succeeded
  • processed_records::Vector{String}: the record names in those batches
  • failed_records::Vector{String}: the record names in the batch that failed
  • error::Exception: the failed batch's error: a REDCapError, or the exception thrown while sending the request

Records

REDCap.export_records — Function
export_records(project; records, fields, forms, events, rawOrLabel, exportCheckboxLabel,
               exportSurveyFields, exportDataAccessGroups, filterLogic, dateRangeBegin,
               dateRangeEnd, decimalCharacter, exportBlankForGrayFormStatus) -> REDCapTable
export_records(project, io::IO; format, rawOrLabelHeaders, csvDelimiter, ...) -> nothing

Export records in the flat format (one row per record, event and repeat instance).

Returns a REDCapTable of strings. The IO method writes REDCap's raw response to io instead, in format :csv, :json, :xml or :odm. For the EAV format, see export_records_eav.

Keyword arguments

  • records: record names to export (scalar or vector)
  • fields: field names to export (scalar or vector)
  • forms: instrument names to export (scalar or vector)
  • events: unique event names to export (longitudinal projects; scalar or vector)
  • rawOrLabel: :raw (default) or :label
  • exportCheckboxLabel: export checkbox values as labels (Bool)
  • exportSurveyFields: include survey identifier and timestamp fields (Bool)
  • exportDataAccessGroups: include the redcap_data_access_group field (Bool)
  • filterLogic: logic string; only records for which it is true are exported
  • dateRangeBegin, dateRangeEnd: only records created or modified after/before this DateTime
  • decimalCharacter: "," or "."
  • exportBlankForGrayFormStatus: export blank instead of 0 for gray (never edited) form status (Bool)
  • batchsize: export in batches of this many records (see below)
  • IO method only: format (required), rawOrLabelHeaders (:raw or :label, CSV only), csvDelimiter (",", "tab", ";", "|" or "^"; CSV only). A CSV-only keyword with another format throws an ArgumentError, as REDCap would ignore it.

Batching

With batchsize=n, the call is split into requests of at most n records each, sent one at a time. All rows of one record stay in the same batch. Batched calls are not atomic: if a batch fails (with an error from REDCap, or a timeout or connection error), a REDCapBatchError reports the progress and wraps the original error, and the earlier batches stay applied.

Without records, a batched export first exports only the record ID field (the first field of the data dictionary), with your filterLogic, date range and events filters, to find the records to export. Batches are not a consistent snapshot: records edited during a long export can produce mixed results. The batches' tables are combined, and must have the same columns; rows come back batch by batch, so when records is given out of order, the row order can differ from an unbatched export. A batched IO export supports format=:csv (one header) and :json (one array) only. With no matching records, a JSON export writes []. A CSV export writes a bare newline, as an unbatched export does, when none of the given records exist, and nothing when records isn't given and no records match.

REDCap.import_records — Function
import_records(project; data, format, forceAutoNumber, dateFormat, csvDelimiter) -> Int

Import records (flat format), adding new records and updating existing ones.

Returns the number of records imported, as reported by REDCap. To get the record names instead, use import_records_ids.

Keyword arguments

  • data (required): a Tables.jl table, a single row (NamedTuple or AbstractDict), or a vector of rows, sent as JSON (a NamedTuple or AbstractDict whose values are all vectors is a column table); or pre-formatted data as an IO or REDCapFile, together with format. A plain String is not accepted.
  • format: required with IO/REDCapFile data, not allowed otherwise: :csv, :json, :xml or :odm
  • forceAutoNumber: let REDCap assign record names; the names in data are only used to group rows (Bool)
  • dateFormat: format of date values in data: :YMD (default), :MDY or :DMY. With table data, Date values are written in this format (yyyy-mm-dd, mm/dd/yyyy or dd/mm/yyyy)
  • csvDelimiter: delimiter of CSV data: "," (default), "tab", ";", "|" or "^". Only accepted with format = :csv; with table data (sent as JSON) or another format it throws an ArgumentError, as REDCap would ignore it
  • batchsize: import in batches of this many records (table data only)
  • recordIdField: the record ID column used to group rows into batches; by default the first field of the data dictionary (with batchsize only)

Blank values in data are ignored; existing values are never erased (see overwrite_records for that).

Batching

With batchsize=n, the call is split into requests of at most n records each, sent one at a time. All rows of one record stay in the same batch. Batched calls are not atomic: if a batch fails (with an error from REDCap, or a timeout or connection error), a REDCapBatchError reports the progress and wraps the original error, and the earlier batches stay applied. With forceAutoNumber=true, the record names in data are only used for grouping. The batched result is the sum of the batches' counts.

A single (unbatched) request is all-or-nothing: if any row is invalid, nothing is imported.

REDCap.import_metadata — Function
Destructive

Replaces the entire data dictionary. Fields missing from data are removed from the project, along with their data.

import_metadata(project; data, format) -> Int

Import a data dictionary. Returns the number of fields imported, as reported by REDCap.

REDCap reads each row of a data dictionary by column position, not by column name, even in JSON. Table data is therefore sent with the columns in REDCap's order (field_name, form_name, section_header, field_type, …, field_annotation, as export_metadata returns them), whatever their order in data; missing columns are sent empty, and a column REDCap doesn't define throws an ArgumentError. Pre-formatted IO or REDCapFile data is sent unchanged, so its columns must already be in REDCap's order.

Keyword arguments

  • data (required): a Tables.jl table, a single row (NamedTuple or AbstractDict), or a vector of rows, sent as JSON (a NamedTuple or AbstractDict whose values are all vectors is a column table); or pre-formatted data as an IO or REDCapFile, together with format. A plain String is not accepted.
  • format: required with IO/REDCapFile data, not allowed otherwise: :csv, :json or :xml
